# Что осталось доделать

Проект уже похож на рабочий MVP, но до завершённого production-like backend осталось несколько важных задач.

## 1. Убрать демонстрационную загрузку при запуске

Сейчас API автоматически создаёт пользователя и загружает `movie.mov` при каждом старте (`cmd/api/main.go`). Это отладочное поведение нужно удалить.

## 2. Исправить гонку между загрузкой и сборкой мусора

Физический blob создаётся раньше записи метаданных, поэтому `CollectGarbageBlobs` может удалить его во время загрузки.

Возможные решения:

- координация через PostgreSQL-lock;
- staging-каталог, который не обрабатывается сборщиком мусора;
- явное состояние жизненного цикла blob.

## 3. Защитить blob-границу

`AddBlob` принимает произвольные `Hash` и `Size`, а hash напрямую используется как часть пути. Необходимо проверять:

- формат SHA-256;
- неотрицательный размер, не превышающий `BlobsMaxSize`;
- существование физического файла;
- соответствие содержимого заявленному хэшу и размеру.

## 4. Сделать `Rename` и `Delete` атомарными

`Rename` сначала читает строку, затем обновляет её и не проверяет `RowsAffected`. При конкурентном удалении он может сообщить об успешном переименовании уже удалённого файла.

Следует использовать `UPDATE ... RETURNING` и `DELETE ... RETURNING`, атомарно возвращая `ErrFileNotFound` при отсутствии строки.

## 5. Не создавать orphan blobs для несуществующих upload

`AddData` и `AddReader` сначала записывают blob на диск и только потом проверяют logical file в PostgreSQL. Отклонённый запрос может оставить физический файл без метаданных.

Проверку существования активной загрузки нужно выполнять до физической записи либо гарантированно очищать созданные blob.

## 6. Сделать очистку неудачных загрузок надёжной

В `UploadData` и `UploadReader` ошибки удаления сейчас игнорируются, а `context.WithoutCancel` не устанавливает дедлайн.

Нужны:

- отдельный ограниченный cleanup-контекст;
- возврат или логирование ошибки очистки;
- механизм удаления давно брошенных загрузок.

## 7. Проверять целостность при чтении

`ReadBlob` проверяет только наличие указанного количества байтов. Он не пересчитывает SHA-256 и не обнаруживает лишние данные после заявленного размера.

Нужно проверять хэш при чтении либо добавить отдельную операцию проверки целостности хранилища.

## 8. Запускать PostgreSQL-тесты в CI

Команды `go test ./...`, `go vet ./...` и `go test -race ./...` проходят, но без переменных окружения почти все integration-тесты `internal/data` пропускаются.

CI должен:

1. Запускать PostgreSQL.
2. Применять миграции.
3. Запускать integration-тесты и race detector.
4. Завершаться ошибкой, если PostgreSQL-тесты были пропущены.
5. Изолировать состояние отдельных тестов.

## 9. Доработать эксплуатационную часть

- Флаг `-blob` сохраняется в конфигурацию, но фактически не меняет максимальный размер blob.
- Мигратор успешно завершается, если каталог `migrations` отсутствует или пуст.
- `Dockerfile` запускает только тесты и не создаёт runtime-образ API.
- В репозитории нет CI и compose-конфигурации для API с PostgreSQL.
- 80-МБ файл `internal/data/testdata/movie.mov` лучше заменить генерируемыми детерминированными тестовыми данными.
- Для приватных данных стоит использовать права `0700` для каталога и `0600` для blob-файлов.
- `BlobsMaxSize` лучше сделать константой или неизменяемой настройкой экземпляра хранилища вместо изменяемой глобальной переменной.

## Рекомендуемый порядок

1. Убрать демонстрационную загрузку при запуске.
2. Закрыть гонку между upload и garbage collection.
3. Добавить валидацию blob и защиту путей.
4. Сделать `Rename` и `Delete` атомарными.
5. Не допускать появления orphan blobs и улучшить cleanup.
6. Настроить обязательные PostgreSQL-тесты в CI.
7. Добавить проверку целостности.
8. Доработать Docker, миграции и документацию запуска.
